# AGENTS.md

Инструкции для AI-агентов (Cursor, Codex и т.п.), работающих в этом
репозитории. Подробности по каждому пункту — в [docs/PIPELINE.md](docs/PIPELINE.md).

## Проект вкратце

Django-сайт (`public_html/`) для листков с задачами по математике: кабинеты
учителя/ученика, база задач, конструктор листков, генерация PDF через
внешний LaTeX API, проверка ответов. Стили — Tailwind CSS v4 standalone CLI,
собранный `app.css` коммитится в git (Node на сервере не нужен). Прод —
`math.emukhin.ru` на Timeweb, обновления вручную: `deploy/deploy.sh`
(см. [deploy/DEPLOY.md](deploy/DEPLOY.md)).

## Локальный запуск и проверки

```bash
python3.12 -m venv venv   # подойдёт и 3.10–3.13
./venv/bin/pip install -r requirements.txt
(cd public_html && ../venv/bin/python manage.py migrate)

make check        # build-css + manage.py test + проверка, что app.css свежий
make build-css    # только пересборка Tailwind
make watch-css    # пересборка в фоне при правке шаблонов/CSS
make test         # только Django-тесты
```

`make`-команды запускаются из корня репозитория — не оставайся в
`public_html` после `migrate`/`runserver`, иначе `make` не найдёт корневой
`Makefile`.

Перед любым коммитом с изменениями в шаблонах, `input.css` или Python-коде
обязательно гоняй `make check` и чини всё, что он находит.

## Сначала localhost, потом Git

Жёсткий порядок работы: **любое изменение сначала делается в локальной
рабочей копии и проверяется вручную на localhost — и только потом (или
одновременно) коммитится и уходит в PR**. Запрещено состояние, когда код
включён в какой-либо PR, но его нельзя увидеть и пощупать на локальной
машине.

```bash
(cd public_html && ../venv/bin/python manage.py runserver)
# http://127.0.0.1:8000
```

- Перед сдачей работы оставь в рабочей копии ту ветку (или локальную
  интеграционную сборку, например `preview`), где лежит **весь** результат:
  при стеке PR — верхняя ветка стека плюс merge независимых веток,
  чтобы пользователь видел всё сделанное сразу.
- Собери CSS (`make build-css`) и проверь затронутые страницы в браузере
  до пуша, а не после.
- Не оставляй checkout на `main`, пока изменения ещё в ветках: пользователь
  запускает `runserver` локально и должен видеть всё, что сделано.

## Конвенции

- Комментарии, docstring'и и сообщения коммитов — на русском, в стиле
  существующей истории репозитория.
- Не переименовывай стабильные CSS-классы/ID без необходимости: `.btn`,
  `.card`, `.ws-*`, `.icon-btn`, `context-sidebar`, `context-toggle`,
  `sidebar-close`, `sidebar-backdrop`, `#ws-saved` — на них завязаны шаблоны
  и JS (`shell.js`, `autosave.js`, `builder.js`).
- Кнопки и крестики удаления — стандарт в [docs/PIPELINE.md](docs/PIPELINE.md),
  раздел «Кнопки и символы закрытия»: обычное действие как «К базе задач»
  (`.btn.btn-secondary`), Сохранить/Отправить/Добавить/PDF — то же, но
  заливка `.btn`, точечное удаление — `.icon-btn` (`×`), не красная кнопка.
- Отступы в формах — там же, раздел «Отступы в формах»: поле ↔ кнопка
  только `--space-2` (8px), заголовок блока ↔ поля — `--space-3` (12px),
  `--space-1` (4px) внутри контрола, не между полем и кнопкой.
- Уведомления об успехе — тост `#ws-saved` справа снизу (`EgorAutosave.showSaved`),
  не новые плашки `.msg-success`. Подробности — в [docs/PIPELINE.md](docs/PIPELINE.md),
  раздел «Уведомления пользователя».
- Новый повторяющийся набор Tailwind-утилит — в `@layer components`
  (`public_html/static/css/input.css`), а не длинной строкой `class="..."`
  по шаблонам.
- Основные разделы приложения — только в горизонтальной навигации
  `base.html`. Боковая панель (`{% block sidebar %}`,
  `public_html/templates/includes/sidebar/`) — только контекст текущей
  страницы, без дублирования верхнего меню.
- Не коммитить: `venv/`, `db.sqlite3`, `media/`, `.secrets/`,
  `public_html/staticfiles/`, `tools/tailwindcss` (уже в `.gitignore`).
- Ключ LaTeX API и другие секреты — только из `.secrets/` или переменных
  окружения, никогда не печатать и не коммитить их значения.

## Роли и доступ к общей базе задач

Учителей несколько, база задач одна. Политика доступа — только в
`public_html/accounts/permissions.py`: `is_base_editor(user)` (суперпользователь
или `Profile.base_editor`), `can_edit_task(user, task)`, `visible_tasks(user)` /
`catalog_tasks(user)`, декоратор `base_editor_required`. Правила:

- `Task.is_shared` — задача в общей базе. Новые задачи создавать только через
  `Task.new_for(user, …)` или `make_variant(user)`: флаг выставляется по тому,
  кто создаёт (редактор базы → общая, приглашённый учитель → личная);
  локальные копии листков (`variant_of`) всегда личные.
- Приглашённый учитель общую задачу **не меняет ни одним путём**: любая запись
  в `Task` и связанные модели проходит через `can_edit_task`, иначе 403 (для
  fetch — JSON `{ok: false, message}`); в листке правки уходят в локальную
  копию (`scope=local`, `data-base-locked` в карточке и `chooseScope` в
  `problem_editor.js`).
- Каталог, поиск, корзина и подбор кандидатов берут базу из
  `visible_tasks`/`catalog_tasks`, а не `Task.objects` напрямую; чужая личная
  задача — 404. Дедупликация импорта — `dedup_tasks` (общие плюс свои, у
  редактора тоже). Счётчики рубрикатора — только по общим задачам.
- Импорт задачников, сверка корпуса, массовые ответы, запись AI-ответов в
  задачи — только редакторам (`base_editor_required`, `is_base_editor` в
  шаблонах). Новые проверки `is_superuser` не добавлять — расширять
  `permissions.py`. Подробности и план: [docs/USERS_PLAN.md](docs/USERS_PLAN.md).
- Учителя регистрируются только по приглашению (`accounts.TeacherInvite`,
  `/accounts/join/<token>/`); выписывает и отзывает их, сбрасывает пароли и
  отключает учителей суперпользователь на странице «Учителя»
  (`superuser_required`, не `is_staff`). Ученик по ссылке
  `/accounts/register/?t=<Profile.student_code>` записывается к владельцу
  кода, без кода — к `default_teacher()`. Общие поля и валидаторы форм
  регистрации — в `accounts.forms.RegistrationForm`.
- Исправления общей базы от приглашённых — очередью предложений
  (`problems.TaskProposal`, `problems/proposals.py`), **только текстом**
  (решение 7 от 19.10.2026): «Предложить исправление» на карточке общей
  задачи и «Предложить маску» из самостоятельных открывают один диалог с
  полем «Что исправить»; у своих задач и локальных копий предложения нет.
  Редактор (`base_editor_required`) на `/problems/proposals/` читает текст,
  правит задачу сам на карточке и ставит статус «Принято» / «Отклонено»
  (`proposal_accept` / `proposal_reject`, без текста ответа); автор видит
  статус в «Мои предложения». Снимков полей, копий-версий и применения по
  полям нет — не возвращать. Счётчики в шапке и кабинете — контекст-процессор
  `shell`; почта — только при настроенном `EMAIL_HOST` и
  `PROPOSAL_NOTIFY_EMAILS` (`problems/notifications.py`), локально при
  `DEBUG` письма идут в консоль.
- Решения 18.10.2026 (PR 3а, `problems/test_decisions.py`): редактор базы по
  умолчанию **не видит** чужие задачи не из общих в каталоге, поиске, фасетах
  и подборе — тумблер «Показывать задачи других учителей»
  (`Profile.show_foreign_tasks`, учитывается в `catalog_tasks`; по прямой
  ссылке, в корзине по id и в предложениях — `visible_tasks`/`cart_tasks`,
  открывается всегда). Нейрогенерация (`task_neuro_solve`) — только
  редакторам, остальным кнопки AI показываются `disabled` с подсказкой
  (`includes/ai_button.html`). Публикацию подборки «всем учителям»
  (`collection_publish`) делает только редактор, снять с публикации может и
  владелец. Слова интерфейса: раздел —
  «Задачи», свои задачи — «Мои задачи» (бейдж «моя», редактору — «задача Имя
  Фамилия»), очередь — «Предложения исправлений», в прозе «общая задача» /
  «моя задача»; «общая база» и «личная» — только в комментариях кода и docs
  (тест гигиены шаблонов и JS).
- Решения обхода 19.10.2026 (раздел 15 плана, PR `feat/users-review-fixes`):
  роль в интерфейсе — «редактор» без «базы» («редактор базы», «редакторам
  базы» запрещены тем же тестом гигиены; исключение — колонка «Можно ред.
  базу» на странице учителей). Кнопки нейрогенерации — одно меню «AI»
  (`includes/ai_menu.html`, `kind=card|form|worksheet`), не-редактору оно
  `disabled` с подсказкой. Не-редактору в форме задачи и на карточке — одно
  поле «Ответ» / «Решение» (`editor.simple_answers`: редакторские поля,
  авторские скрыты, пока у задачи нет авторских ответов и источника).
  Логины — фамилия и имя через точку (`generate_username`, `registration.js`).
  Бейдж локальной копии — `.badge-local` (фиолетовый), чужой задачи у
  редактора — «автор: Имя Фамилия». Сбой LaTeX API учитель видит общей фразой
  (`LatexCompileError.user_message`), подробности — только суперпользователю.
- Онбординг (PR 4, раздел 7 плана): чеклист «Первые шаги» —
  `accounts/onboarding.py` (прогресс только по данным: имя, ученики, листок,
  выданное задание; хранится лишь `Profile.onboarding_done_at` — кнопка
  «Скрыть»), страница `/accounts/welcome/` (редирект после регистрации по
  приглашению), карточка в кабинете учителя без права редактора,
  исчезает сама после первого выданного задания. Пустые состояния
  («Ученики», «Листки», «Задания», «Самостоятельные», кабинет) ведут к
  следующему шагу; флаг `shows_onboarding` из контекст-процессора `shell`.
  Справка для учителей — `docs/USERS.md` и `/help/teachers/`
  (`templates/help/teachers.html`, ссылка в футере учителя). Подсказка на
  общей задаче в листке — `[data-shared-task-hint]`, `localStorage` в
  `problem_editor.js`.

## Git-pipeline: обновления → PR → ревью → правки

Прямые коммиты в `main` не используем — только ветки и pull request'ы.

```
ветка → make check → PR в GitHub → ревью → правки новыми коммитами → повторное ревью → merge в main
```

1. Создать ветку от актуального `main`: `feat/<что>`, `fix/<что>`, `ui/<что>`,
   `docs/<что>`.
2. Внести изменения, прогнать `make check`, закоммитить (сообщения — по-русски,
   по сути изменения).
3. Запушить ветку и открыть PR в GitHub-репозиторий
   (`git@github.com:emukhin96/egormath.git`) с описанием: что изменилось,
   какие экраны/модули затронуты, что проверено вручную. Агент без SSH-ключа
   делает это через `tools/pr.sh push` и `tools/pr.sh open` (токен в
   `.secrets/GITHUB_TOKEN`, см. раздел 5 docs/PIPELINE.md); merge, rebase и
   force-push агенту запрещены — сливает только человек.
4. Ревью — комментарии в PR. CI (`.github/workflows/ci.yml`) должен быть
   зелёным: тесты + проверка, что `app.css` пересобран.
5. Правки по ревью — **новые коммиты в ту же ветку**, без `--amend` и
   force-push (иначе комментарии ревьюера отвязываются от строк).
6. Отправить исправления в GitHub (push той же ветки) и **обязательно
   ответить в каждом inline-треде** через `tools/pr.sh reply`, а на каждый
   общий комментарий PR (в том числе автоматическое ревью бота) — через
   `tools/pr.sh comment <id>`: подтверждённое замечание — «исправлено
   в <sha>», спорное — аргументированный отказ.
   `tools/pr.sh status` помечает треды «⚠ без ответа» — их не должно
   остаться. Затем повторное ревью тех же или новых замечаний, пока не
   будет апрув.
7. После апрува — merge в `main` (обычно squash или обычный merge, без
   rebase истории ветки в процессе ревью).

Чеклист перед тем, как просить ревью, — в разделе 5
[docs/PIPELINE.md](docs/PIPELINE.md).

  изменений в генерации `.tex` (`worksheets/latex.py`, импорт, картинки
  задач). Вызывать проактивно после таких изменений, до открытия PR.
