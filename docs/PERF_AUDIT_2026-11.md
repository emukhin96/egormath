# Аудит быстродействия сайта — 06.11.2026

Что замедляет загрузку страниц каждого раздела, что можно улучшить и во что это
обойдётся. Все цифры — из замеров (стенд с копией прода `egormath_shot`,
29 828 задач, 3 131 листок, и сам прод `math.emukhin.ru` из залогиненного
Chrome). Сырые данные и скрипты — в `artifacts/perf-2026-11/`.

## 1. Коротко

Сайт медленный не из-за сети и не из-за статики — они настроены хорошо
(HTTP/2, zstd, хэшированные имена с кэшем на год). Медленно работает
**Python на сервере**: на проде до первого байта (TTFB) уходит 1–2,6 с на
кабинете учителя, каталоге задач, подборках, самостоятельных и больших
листках, тогда как сеть добавляет лишь ~0,1–0,3 с.

Четыре причины дают почти всё время:

| # | Причина | Где | Сколько стоит (локально → прод ≈ ×2,5) |
|---|---------|-----|------------------------------------------|
| 1 | **Разбор масок ответов (sympy/lark) при каждом показе страницы**, без кэша | кабинет учителя, каталог самостоятельных, страница попытки ученика | 0,7–1,2 с на страницу → 1,5–2,5 с на проде |
| 2 | **Тяжёлые COUNT по 30 тыс. задач с DISTINCT по всем полям** и счётчики рубрикатора по одному запросу на раздел | каталог задач | 0,5–0,6 с SQL из 0,7 с → ~1,5 с на проде |
| 3 | **Каталог подборок читает все 3 074 подборки с полными строками листков** на каждый запрос | подборки, карточка подборки | 0,4 с SQL + 0,3 с распаковки строк → 1,7 с на проде |
| 4 | **Огромный HTML**: конструктор листка на 366 задач — 3,8 МБ, 95 тыс. DOM-узлов, 3 262 формы; списки заданий и самостоятельных — 0,5–0,6 МБ из-за диалога с `<select>` на каждого ученика | листки, задания, самостоятельные | рендер шаблона 0,4–1,9 с, в браузере ещё 0,5–1 с на разбор и KaTeX |

Что делать в первую очередь (подробно — раздел 7): кэш разбора масок
(2–4 ч работы, минус 1–2 с с трёх ключевых страниц), облегчение счётчиков
каталога (3–6 ч), кэш дерева подборок (3–5 ч), ленивые диалоги в списках
заданий (4–8 ч). Всё это — обычные PR без изменения инфраструктуры; суммарно
1–2 рабочих дня. Переезд на более мощный VPS **не нужен** до этих правок:
2 vCPU делятся с chemolymp и latex-api, но проблема в количестве работы на
запрос, а не в железе.

## 3. Прод: что уже хорошо

- Два Caddy, HTTP/2, `encode zstd gzip` — HTML каталога 206 КБ уходит как
  24 КБ, конструктор 3,8 МБ — как 167 КБ.
- Статика после `collectstatic` с хэшем в имени и `Cache-Control: immutable,
  max-age=1 год`; отдаёт Caddy, Django не участвует. Файлы живых страниц
  `/live/*.txt` тоже мимо Django.
- gunicorn `gthread` 2×4, `CONN_MAX_AGE=60` — соединение с MySQL не
  открывается на каждый запрос.
- Каталог рубрикатора — отдельный `taxonomy.json` (63 КБ) с файловым кэшем
  и ETag; в страницы не встраивается.
- Контекст-процессор `shell`: счётчики предложений ленивые; у ученика
  лишних запросов нет.
- `/healthz` (с запросом к БД) отвечает за ~140 мс с учётом RTT; страница
  входа — ~110 мс сверх TLS. То есть «пустой» запрос к Django на проде
  стоит около 0,1 с; всё, что выше, — работа конкретной страницы.

### 4.2. Инфраструктура

- VPS 2 vCPU / 4 ГБ общий с chemolymp и latex-api; `egormath-web` ограничен
  700 МБ, MySQL 512 МБ (`innodb_buffer_pool_size=256M` — вся база ~150 МБ
  помещается, диск не узкое место).
- gunicorn 2 воркера × 4 потока. Все медленные страницы — CPU-bound Python
  (GIL), поэтому реально одновременно считаются 2 запроса. Класс из 25
  учеников, открывающих попытку самостоятельной (0,34 с на Mac ≈ 0,85 с на
  VPS каждая), выстраивается в очередь: последний получит страницу через
  ~10 с, если ничего больше не происходит.
- RTT до сервера из Москвы ~80–100 мс; DNS 0,2 с на холодном старте.

## 5. Разбор по разделам

### Кабинет учителя — 408 мс локально, 1,1–2,4 с на проде

Профиль: 79 % времени — `teacher_home.review_groups` →
`independentworks.integration.attempt_status` → `services.result` →
`parse_mask` → `expressions.raw_tree` (lark + sympy). Для статуса
«ждёт проверки» каждой попытки кабинет разбирает маски всех пунктов всех
незакрытых проведений (265 вызовов `parse_mask`, из них 10 формульных масок
дали 0,69 с). Разбор повторяется при каждом открытии кабинета любым учителем
и ничем не кэшируется (`grep lru_cache assignments/checks/` пуст).

SQL 122 мс: `Worksheet.visible_to(...).annotate(items_total=Count('items'))[:5]`
группирует все 3 131 листок с их элементами ради пяти последних (54 мс);
`catalog_tasks(user).count()` — полный проход по задачам (43 мс).

### Задачи — 0,6–0,7 с локально, 1,5–1,7 с на проде

Почти всё — SQL (586 из 713 мс), 33 запроса:

- `Paginator.count()` для queryset с `.distinct()` и `prefetch_related`
  превращается в `SELECT COUNT(*) FROM (SELECT DISTINCT <все колонки задачи,
  включая text_latex, solution_latex...> ...)` — 175–220 мс. Второй такой же
  COUNT — 100–120 мс. DISTINCT по текстовым полям на 30 тыс. строк —
  самая дорогая операция каталога.
- `_rubricator_blocks`: по одному `COUNT(DISTINCT)` на корневой раздел
  рубрикатора, а при открытом разделе — ещё по подразделам (87 запросов на
  `?topic=1`), итого 0,42 с под профилем.
- `_catalog_facets`: агрегат по классам с `COUNT(DISTINCT CASE …)` по
  всем задачам (64 мс) и топ источников (91 мс).
- Поиск по `text_plain__icontains` — полный скан, но он дешевле счётчиков.

Эти счётчики почти не меняются между запросами (общие задачи одни на всех),
но считаются заново для каждой страницы, страницы пагинации и каждого
учителя.

### Подборки — 0,7–0,8 с локально, 1,7 с на проде

`_collection_catalog` загружает все 3 074 подборки через
`select_related('worksheet', 'source', 'parent')` + `prefetch_related
('worksheet__topics')` + `annotate(Count(...))`: один запрос 311 мс, распаковка
11 136 пакетов MySQL ещё ~0,3 с Python, потом обход дерева. Нужны же только
id, названия, родитель, флаг публикации и счётчик — а грузятся все поля
листка (включая тексты). Карточка подборки строит то же дерево заново
(432 мс SQL).

### Листки

Список — быстрый (104 мс), но HTML 252 КБ: 255 инлайн-форм и 58 компактных
рубрикаторов на 58 строк. Сжимается до 14 КБ, на проде TTFB 0,3 с — терпимо.

Конструктор большого листка (366 элементов): рендер шаблона 1,9 из 2,6 с
под профилем (66 тыс. узлов шаблона, 5 505 include), `attach_usage` 0,34 с
(история выдач по всем задачам листка), `tex_to_web_html` 2 932 вызова
0,28 с. На каждый элемент — ~9 форм с CSRF-токеном, диалог настроек
(`settings-N`), диалог видимости (`vis-N`), набор SVG-иконок: 3 262 формы,
362 диалога, 720 SVG. Браузер получает 95 тыс. DOM-узлов и 1 125 формул.
Редактор PDF того же листка — 3,3 МБ и 17 повторяющихся SQL-запросов
(подпункты грузятся по одному).

### Задания — 0,2 с локально, 0,65 с на проде

Серверное время невелико, но HTML 602 КБ: для каждого из 20 листков в
очереди рендерится диалог «получатели» с чекбоксом и `<select>` статуса на
каждого из 19 учеников (386 селектов, 4 687 опций). Рендер шаблона — 0,45 с
под профилем, 94 % времени страницы. Живая страница и хронология задания
делают до 12 одинаковых запросов «последние листки/самостоятельные» —
контекст-процессор `shell` вызывает `cart_context` при каждом
`render_to_string` частичного шаблона.

### Самостоятельные — 0,8 с локально, 1,7 с на проде

Каталог переиспользует `assignment_list`, а тот через
`integration.assignment_groups` → `attempt_status` снова разбирает маски
(530 вызовов `parse_mask`, 1,16 с из 1,88 с под профилем) — та же причина,
что в кабинете. Плюс диалог получателей с `<select>` варианта на каждого
ученика (528 КБ HTML, 253 селекта) и 12 дублей запросов.

### Ученики

Список учеников — 31 мс. Страница учителей — 109 мс в одном запросе:
`DISTINCT auth_user.*` с двумя `COUNT(DISTINCT)` по ученикам и листкам —
на 2 учителей это избыточно, но страница редкая.

### Страницы ученика

Кабинет и обычное задание — 23–25 мс (отлично). **Попытка
самостоятельной — 340 мс при 5 мс SQL**: `point_rows` вызывает `parse_mask`
на каждый пункт (12 масок, 8 формульных дали 0,92 с под профилем) и ещё раз
в `answer_display`. На проде это ~0,85 с на каждое открытие и
**каждую перезагрузку** страницы в ходе самостоятельной — самая
чувствительная к нагрузке страница сайта, потому что её открывает весь
класс одновременно.

## 6. Что можно улучшить и сколько это стоит

Оценки — часы работы (агент + ревью + проверка на стенде), риск — для
поведения сайта. Эффект — локальные мс; на проде умножать на ~2,5.

### Приоритет 1: быстрые и дешёвые (1–2 дня суммарно, минус 1–2 с с главных страниц)

| # | Правка | Эффект | Стоимость | Риск |
|---|--------|--------|-----------|------|
