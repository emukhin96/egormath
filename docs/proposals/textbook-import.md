# Импорт распознанных задачников: проект решения

Статус: базовый импорт, ручная очередь и подборки реализованы. CLI-парсер
по-прежнему формирует проверяемые артефакты и сам не пишет в базу данных;
загрузка выполняется отдельным транзакционным контуром после проверки.

## Что показали четыре примера

Файлы относятся к трём различным профилям, а не к одному формату LaTeX.

- **Галицкий**: задачи имеют глобальные номера `1.1`, `1.2`, …; ответы,
  указания и редкие решения находятся в плотном разделе в конце файла.
- **Зив**: номер задачи локален внутри сочетания «тип работы → тема →
  вариант». Одинаковые `1`, `2`, … встречаются сотни раз, поэтому номер без
  полного пути не является идентификатором.
- **Шестаков**: книга задач и решебник связываются кодом `1.1.A01`.
  Это самый надёжный профиль для автоматического merge, но OCR двухколоночных
  страниц местами смешал порядок блоков. Встречаются также варианты записи
  `\item[1.1.] В02`, которые нужно нормализовать в `1.1.B02`.

Первый прогон прототипа дал ориентировочные, но полезные числа:

| Профиль | Выделено задач | Сопоставлено ответов/решений | Особенность |
| --- | ---: | ---: | --- |
| Шестаков | 1202 | 1132 | 167 блоков требуют внимания, в основном из-за порядка колонок |
| Галицкий | 1822 | 880 | отсутствие ответа у многих задач нормально; плотная строка ответов хрупка |
| Зив | 771 уникальный черновик из 891 маркера | пока 0 | нужен полный ключ работа/тема/вариант/номер |

Это не числа для загрузки: они характеризуют OCR и используются как baseline
для следующих итераций профилей.

### Повторный пилот Шестакова

После AST-разбора вложенных списков и раздельных правил маркеров для задачника
и решебника профиль даёт:

- 1202 уникальных блока без дублей, отсортированных по каноническому коду;
- 18 отсутствующих номеров из полной сетки 1220 — они перечислены в
  `missing_task_ids`, а не замалчиваются;
- 1129 однозначно отделённых полных решений;
- у 73 задач нет отдельной границы в решебнике; 55 предшествующих
  блоков консервативно помечены для проверки возможной склейки,
  включая известные пары `10.2.A09/A10`, `10.3.C08/C09` и
  `10.3.C11/C12`;
- 32 задачи по обе стороны 16 нарушений физического порядка колонок помечены
  предупреждением; семь доказуемо вложенных хвостов возвращены соседней
  задаче и перечислены в `detached_column_fragments`;
- экзаменационные приложения после `11.1.D10` отсечены и в задачнике, и
  в решебнике;
- 319 рисунков условий и решений преобразованы в штатные `\taskpic{N}`;
- у задач с подпунктами 1946 фрагментов решения распределены по 973 задачам:
  верхние метки хранятся только как границы и не дублируются в тексте
  `author_solution_latex` подпункта; вложенная содержательная нумерация
  сохраняется;
- явные строки `Ответ:` дополнительно извлекаются в авторские поля ответа
  задачи или соответствующего подпункта (719 задач);
- при несовпадении количества или меток подпунктов условия и решения автоматического
  распределения нет: полный блок остаётся у задачи и получает предупреждение;
- 174 блока входят в ручную очередь; остальные 1028 не имеют структурных
  предупреждений парсера.

Таким образом, физическая двухколоночная раскладка не воспроизводится, но её
влияние на границы остаётся явно видимым в отчёте и очереди проверки.

## Конвейер

```text
OCR-LaTeX
  → профиль конкретного задачника
  → нейтральный import.json
  → review.tsv + report.md
  → ручная проверка/исправление
  → строгая валидация
  → dry-run против Django DB
  → транзакционная идемпотентная загрузка одобренных строк
```

Разделение на extract и load обязательно. Ошибка распознавания не должна
попадать в рабочую базу только потому, что парсер смог найти похожий номер.

### Как посмотреть результат локально

Пошаговая пользовательская инструкция хранится в
[`docs/TEXTBOOK_IMPORT_USER_GUIDE.md`](../TEXTBOOK_IMPORT_USER_GUIDE.md) и
дублируется в самом интерфейсе: **Импорт → Инструкция**. Каталог дефектов
парсинга и канон оформления черновиков —
[`docs/TEXTBOOK_PARSE_QA.md`](../TEXTBOOK_PARSE_QA.md).

1. Из корня репозитория сформировать `var/imports/<profile>/import.json`
   командой парсера и запустить сайт:

   ```bash
   (cd public_html && ../venv/bin/python manage.py runserver)
   ```

2. Войти учителем или администратором, открыть **База задач**, а затем в
   контекстной панели — **Импорты задачников**. Прямой адрес:
   `http://127.0.0.1:8000/problems/imports/`.
3. Кнопка **Новая партия** загружает `import.json` только в черновую очередь.
   До действия **Загрузить в каталог** рабочие задачи и подборки не меняются.
4. На странице партии доступны статусы и постраничный список. Нажатие на
   ключ задачи открывает ручную сверку условия, подпунктов, темы, авторского
   ответа и решения. Предупреждения парсера показаны над формой.

Локальная `db.sqlite3` и артефакты `var/imports/` не коммитятся. Поэтому для
ручной проверки конкретного пилота партия должна быть загружена отдельно в
каждой рабочей копии.

### Промежуточная задача

Каждая строка `import.json` содержит:

- `external_id` — стабильный канонический ключ внутри издания;
- `source_number` — показываемый пользователю номер;
- `source_path` — исходная иерархия главы/параграфа/уровня/варианта;
- `collection_key`, `collection_title`;
- `topic_original` и (на следующем этапе) кандидаты кодов рубрикатора;
- условие, подпункты, авторский ответ и решение; редкое авторское указание
  сохраняется в начале/середине решения в исходном порядке;
- `stars=0` — неизменяемое правило для всех задач этого конвейера;
- изображения;
- `confidence`, `warnings`, `review_status`.

TSV нужен как удобный реестр для фильтров и массовых пометок. Источником
истины остаётся JSON: многострочный LaTeX и подпункты плохо укладываются в
CSV/TSV без структурных потерь.

На первом этапе JSON хранит имена найденных изображений, но не их бинарные
данные. Такие строки остаются видимыми в очереди, однако загрузка партии
блокируется: файл нельзя публиковать с битой `\\taskpic`/`\\includegraphics`.
Отдельный asset-bundle и экран сопоставления файлов — следующий этап.

## Сопоставление с рубрикатором

Название из книги нельзя автоматически превращать в новую `Topic`.

1. Нормализовать регистр, `ё/е`, OCR-пробелы и служебные слова.
2. Сравнить исходный путь с именами существующего дерева `Topic`.
3. Учитывать родительские заголовки: например, «Действия с дробями» под
   «Числовые выражения» точнее одиночной строки.
4. Записать до трёх кандидатов `{code, score, reason}`.
5. Автоматически выбирать только заранее утверждённые exact-alias правила.
   Fuzzy/AI-кандидат всегда остаётся `needs_review`.
6. Сохранять `topic_original` после импорта для аудита и последующего
   улучшения словаря aliases.

Первичную тему следует создавать через `TaskTopic(role=PRIMARY,
relevance=1.00)`. Дополнительные темы — только после ручного решения или
отдельной классификации текста задачи.

## «Подборки»: тот же редактор и PDF-контур, что у листков

Подборка отличается от личного листка происхождением и местом в каталоге, но
**не возможностями содержимого**. В ней должны без расхождений работать:

- перестановка и мягкое удаление/восстановление задач;
- переопределение звёзд и числа колонок внутри конкретной подборки;
- выбор отдельных подпунктов задачи;
- рубрики и произвольные теоретические вставки всех существующих стилей
  (`plain`, `rule`, `light`, `memo`);
- тот же редактор, автосохранение, предпросмотр и три варианта PDF;
- тот же сбор картинок, LaTeX API, диагностика компиляции и PDF-кэш;
- копирование подборки в личный листок с сохранением порядка и настроек.

Поэтому отдельный `CollectionItem` создавать не нужно: он неизбежно
продублировал бы `WorksheetItem` и со временем разошёлся с конструктором.
Предлагается тонкая каталожная оболочка над обычным листком:

```python
class Collection(models.Model):
    worksheet = OneToOneField(
        Worksheet, on_delete=CASCADE, related_name='collection')
    source = ForeignKey(Source, PROTECT, related_name='collections')
    parent = ForeignKey('self', CASCADE, null=True, blank=True)
    source_path = JSONField(default=list)
    order = PositiveIntegerField(default=0)
    is_published = BooleanField(default=False)
```

Название, темы, классы и всё содержимое живут в связанном `Worksheet`.
Иерархия книги становится деревом `Collection`; листья — виртуальные
листочки. Одна задача может находиться в нескольких подборках через разные
`WorksheetItem` (например, в параграфе, тематической серии и экзаменационной
работе).

Для каталожной подборки нужен назначенный редактор-владелец `Worksheet`
(администратор/куратор импорта), поэтому ослаблять обязательность `owner` не
требуется. Права просмотра определяются `Collection.is_published`, а права
редактирования — существующей проверкой владельца/администратора. Действие
«Использовать подборку» вызывает существующий `Worksheet.duplicate()`, меняет
владельца копии на текущего учителя и снимает связь с каталогом.

Перед реализацией требуется один интеграционный тест-контракт: одинаковая
последовательность действий над обычным листком и backing-worksheet подборки
должна создавать одинаковые `WorksheetItem` и одинаковый LaTeX для всех трёх
PDF-вариантов. Это проверит, что у подборок не возник отдельный урезанный
редактор.

## Источник и идемпотентность

Текущего `TaskSource.number` недостаточно для книг вроде Зива. Нужны:

```python
TaskSource.locator       # канонический ключ: sr/01/variant-3/task-4
TaskSource.number        # отображаемый номер: «СР 1, вариант 3, № 4»
TaskSource.source_path   # JSON исходных заголовков
TaskSource.page          # nullable
UniqueConstraint(source, locator)
```

Повторный импорт ищет запись только по `(source, locator)`. Совпадение текста
используется как подсказка для дедупликации между разными источниками, но не
как автоматическое основание слить задачи.

## Авторские, редакторские и AI-данные

Для совместимости существующие `answer_latex` и `solution_latex` остаются
**рабочими полями редактора и уже отлаженного AI-контура**. Импорт их никогда
не меняет. Рядом добавляются поля неизменяемого текста источника:

```python
author_answer_latex
author_solution_latex
```

Те же поля нужны у `TaskSubitem`.

- Импорт книги всегда пишет в `author_*`. Указание присоединяется к
  `author_solution_latex` в том месте, где оно находится в книге.
- Существующая нейрогенерация продолжает писать только в рабочие поля и не
  получает доступа к `author_*`; это закрепляется регрессионным тестом.
- Для показа, проверки ученика и PDF используется `answer_latex`, если оно
  заполнено, иначе `author_answer_latex`; для решения действует тот же
  приоритет. Поэтому импортированный авторский текст работает сразу, но
  редакторский/AI-вариант может безопасно его перекрыть, не уничтожив.
- Отдельные `ai_*`, сведения о модели и workflow принятия AI можно добавить
  следующей миграцией, если понадобится хранить ещё и непринятый AI-черновик.
  Текущая реализация намеренно не переписывает зрелый AI-контур в рамках
  книжного импорта.

Так уже сейчас физически разделены текст автора и рабочее значение, а
существующий AI-функционал остаётся обратно совместимым.

## Звёзды и сложность

Все задачи, созданные книжным импортом, получают `Task.stars = 0`. Парсер
пишет это значение явно, а будущий `load_textbook` принудительно ставит ноль,
не доверяя отредактированному JSON. Звёзды задаются позже только в контексте
листка или подборки через существующее `WorksheetItem.stars_override`.

Это правило не запрещает будущую независимую классификацию технической
сложности (`Task.difficulty`): она не должна автоматически превращаться в
звёзды каталожной задачи.

## Интерфейс ручного сопоставления решений

Ручная проверка должна работать не в огромном TSV, а как очередь внутри
Django. TSV остаётся вспомогательным экспортом.

### Экран партии

Верхняя строка показывает прогресс и фильтры:

- `не проверено`, `низкая уверенность`, `нет решения`, `несколько кандидатов`,
  `дубликат номера`, `нарушен порядок OCR`, `готово`;
- глава/параграф/уровень/вариант;
- полнотекстовый поиск по номеру и фрагменту условия;
- счётчики `проверено / всего` и отдельный счётчик блокирующих конфликтов.

Загрузка партии запрещена, пока есть строки со статусом `conflict` или
`needs_review`. Строка без авторского ответа сама по себе не конфликт: у многих
задач ответ в книге отсутствует.

### Карточка сопоставления

Основная рабочая область делится на две синхронные панели:

1. Слева — условие, подпункты, номер, путь по книге и соседние номера.
2. Справа — выбранный ответ/решение и до трёх соседних кандидатов из книги
   решений. Формулы сразу рендерятся KaTeX, под ними доступен исходный LaTeX.

Между панелями действия:

- «Соответствует»;
- «У задачи нет решения»;
- «Выбрать другой кандидат»;
- «Отвязать»;
- «Объединить фрагменты» — когда одно решение OCR разбил на два блока;
- «Разделить фрагмент» — когда соседние решения склеились;
- «Исправить номер/границу»;
- «Отложить» и «Пометить как ошибку OCR».

После выбора другого кандидата интерфейс обязан показать, не был ли он уже
привязан к другой задаче. Переназначение выполняется атомарно и оставляет
запись аудита: кто, когда, от какого ключа к какому переместил решение.

### Контекст для сложных случаев

Для Шестакова физический порядок двух колонок воспроизводить не нужно.
Парсер нормализует код (`1.1.В02` → `1.1.B02`), выделяет блоки и затем
сортирует итоговый список по каноническому коду. Нарушение линейного порядка
используется только как сигнал возможной склейки текста; рецензент видит
предыдущую и следующую задачи по коду, а также исходный фрагмент вокруг OCR-
границы.

Для Галицкого справа показывается плотная строка ответов с подсветкой границ
соседних номеров. Для Зива ключ всегда включает тип работы, тему, вариант и
локальный номер; совпадение одного `№ 1` не считается кандидатом.

### Горячие клавиши и пакетная проверка

- `A` — соответствует, `N` — решения нет, `E` — редактировать;
- `←/→` — предыдущая/следующая задача;
- `1`–`3` — выбрать кандидата;
- Shift-действие применяет решение к выделенной группе только для полностью
  одинакового нормализованного правила, например exact match кода.

Автопринятие допустимо только для уникального exact match канонического ключа
при структурно валидном LaTeX. Даже такие строки остаются доступными в
фильтре «принято автоматически» для выборочного контроля.

## Команды следующего этапа

```bash
# Только артефакты для проверки
python tools/textbook_parser.py --profile shestakov \
  --tasks shestakov-tasks.tex --solutions shestakov-solutions.tex \
  --output var/imports/shestakov

# Будущая Django-команда: по умолчанию dry-run
python manage.py load_textbook var/imports/shestakov/import.json
python manage.py load_textbook var/imports/shestakov/import.json --commit
```

`load_textbook` должна отклонять строки не в статусе `approved`, работать в
транзакции, печатать create/update/conflict/skip и не менять существующий
проверенный контент без явного флага.

## Порядок реализации

1. **Выполнено:** довести профиль Шестакова: построить AST списков, отделить
   смешанные OCR-блоки и отсортировать задачи по коду; исходную раскладку
   колонок не воспроизводить.
2. Довести Галицкого: точнее выделять плотные ответы и различать
   `Ответ`/`Указание`/`Решение`.
3. Довести Зива: канонический ключ из типа работы, темы, варианта и номера;
   после этого включить merge ответов.
4. Добавить topic aliases и кандидатов рубрикатора.
5. **Выполнено:** внести миграции `author_*`/`ai_*`, `TaskSource.locator` и каталожной
   оболочки `Collection(worksheet=OneToOneField(...))`.
6. Добавить management-команду `load_textbook` с dry-run поверх уже
   реализованного валидатора и транзакционного сервиса.
7. **Выполнено:** добавить экран очереди проверки и разрешить commit только
   для одобренных строк с выбранной темой рубрикатора.

## Критерии готовности профиля книги

- все ожидаемые номера представлены ровно один раз либо перечислены в
  явном conflict-report;
- нет несбалансированных LaTeX-групп и окружений;
- случайная выборка из начала/середины/конца каждого раздела проверена;
- все связи условие↔ответ/решение объяснимы каноническим ключом;
