# Pipeline разработки

Как сейчас работает проект: разработка идёт локально, изменения уезжают в
GitHub (`git@github.com:emukhin96/egormath.git`) через ветки и pull request'ы.
После merge в `main` прод обновляют вручную по SSH:
`/home/c/cs13661/egormath/deploy/deploy.sh`
(инструкция — [deploy/DEPLOY.md](../deploy/DEPLOY.md)).

Короткая версия для AI-агентов (команды, конвенции, чеклист) — в
[AGENTS.md](../AGENTS.md) в корне репозитория.

## 1. Локальная работа

Первый запуск:

```bash
python3.12 -m venv venv   # подойдёт и 3.10–3.13
./venv/bin/pip install -r requirements.txt
cd public_html
../venv/bin/python manage.py migrate
../venv/bin/python manage.py seed_rubricator  # дерево тем 5–11, классы, экзамены
../venv/bin/python manage.py seed_topics      # то же (старое имя команды)
../venv/bin/python manage.py createsuperuser
```

Ежедневно — два терминала:

```bash
# терминал 1: сайт
cd public_html && ../venv/bin/python manage.py runserver

# терминал 2: пересборка стилей при правках шаблонов и CSS
make watch-css
```



### Локальный стенд со слепком прода

Большие правки интерфейса удобно смотреть на реальных данных до деплоя.
`tools/stage.sh` собирает такой стенд на Mac, не трогая прод:

```bash
tools/stage.sh                  # последний ночной дамп + media, worktree на ветке preview (или main)
tools/stage.sh --fresh          # сначала снять новый дамп на сервере (backup.sh)
tools/stage.sh --branch ui/x    # какую ветку показать
tools/stage.sh --run            # сразу запустить runserver на порту 8003
```

Что делает скрипт: копирует с VPS свежий `db-*.sql.gz` (и `rsync` каталога
`media/`), пересоздаёт локальную базу `egormath_stage` в Homebrew MySQL и
заливает дамп, при необходимости грузит таблицы часовых поясов, держит
отдельный worktree стенда и прогоняет миграции ветки поверх дампа. Всё,
что содержит данные прода — дампы, worktree с его `media/`, `SECRET_KEY`
стенда, — лежит в `STAGE_DATA` (по умолчанию
`~/Library/Caches/egormath-stage`), **вне репозитория**: репозиторий
синхронизируется Dropbox, а `.gitignore` от выгрузки в облако не
защищает. У worktree свой каталог `.secrets`: в нём только ссылки на
API-ключи рабочей копии (`LATEX_*`, `GEMINI_*`) и собственный случайный
`DJANGO_SECRET_KEY`; `DB_*` и `DJANGO_ENV` рабочей копии на стенд не
действуют — база задаётся переменными окружения из подсказки скрипта.
Затем печатает команду запуска: `runserver 127.0.0.1:8003`. В базе —
персональные данные и хэши паролей с прода при `DEBUG=True`, поэтому в
сеть стенд не смотрит; с телефона по IP Mac — только флагом `--lan` и
только в доверенной сети. Вход — своим обычным логином (хэши паролей из
дампа); ученические сценарии — сбросив ученику пароль на стенде.

База выбирается переменной `DB_ENGINE=mysql` (иначе в разработке sqlite);
`DB_SOCKET` — сокет локального MySQL, через него не нужен пакет
`cryptography`. Ветка стенда должна содержать этот переключатель (в `main`
с PR «Локальный стенд»). Чего стенд не умеет: сборка PDF и презентаций —
общий latex-api доступен только внутри docker-сети VPS; эти страницы
проверяют на проде после деплоя.

## 2. Стили


| Файл                               | Роль                                                              |
| ---------------------------------- | ----------------------------------------------------------------- |
| `public_html/static/css/input.css` | Единственный источник: токены, `@layer base`, `@layer components` |
| `public_html/static/css/app.css`   | Собранный артефакт, **коммитится вместе с исходником**            |
| `tools/tailwindcss`                | Standalone CLI, качается автоматически, в git не попадает         |


Правила:

- Токены отступов — шкала 4px: `--space-1` … `--space-6`. Новые значения
берём из шкалы, а не «на глаз». Какую ступень брать в форме — в разделе
«Отступы в формах» ниже.
- Tailwind preflight обнуляет отступы и вес заголовков. Всё, что должно
выглядеть как обычный текст (`p`, списки, `h1`–`h6`, `hr`), уже
восстановлено в `@layer base` — не переопределять поштучно в шаблонах.
- Повторяющийся набор утилит выносим в `@layer components`, а не копируем
длинную строку `class="..."` по шаблонам.
- Именованные классы (`.btn`, `.card`, `.ws-*`, `.icon-btn`) — стабильный
контракт для шаблонов и JS, не переименовывать без необходимости.
- Заголовок карточки (`.card > h2`, `.card-head h2`) — ярлык: мелкий,
полужирный, цветом `--muted`; содержимое карточки читается первым.
Рубрики внутри `.ws-view` — содержимое, к ним это не относится.
- Боковая панель светлая (`#fff`, рамка `--border`); navy остаётся у бренда,
заливных кнопок и активных состояний. Активный пункт списка панели —
`li.is-current` (фон `--accent-soft`, текст `--accent`), тот же вид, что у
активного пункта меню.
- Запрещены акцентные рамки с одной стороны (`border-top/left/right/bottom`
цветом `--accent` и т.п.): выделять панели только фоном или тенью.
- Основные разделы приложения живут только в горизонтальной навигации
`base.html`. Боковая панель заполняется через `{% block sidebar %}` и содержит
только контекст открытой страницы: навигацию внутри раздела (рубрикатор,
темы, главы источника, группы, якоря задач) и сведения, которых нет в
содержимом. Действие живёт в одном месте: кнопки страницы — в её шапке или
панели инструментов, в боковой панели их не дублируем; счётчики — в
содержимом (`.stat-strip`), не в плитках панели. Если у страницы нет
контекста, блок оставляют пустым: панель и кнопка «Контекст» скрываются
CSS (`.context-sidebar` без `.sidebar-section`), содержимое занимает всю
ширину.
- Переиспользуемые панели лежат в `public_html/templates/includes/sidebar/`.
На экране до 760px панель открывает `static/js/shell.js`; при изменении
разметки сохраняйте ID `context-sidebar`, `context-toggle`,
`sidebar-close` и `sidebar-backdrop`.

### Кнопки и символы закрытия

Эталон обычной кнопки — «К базе задач» на карточке задачи:
`.btn.btn-secondary` (белая, рамка `--border`, текст `--accent-dark`).
Размер один: `min-height: 36px`, `padding: 7px 14px`. Кнопка — обычный
элемент (`width: max-content`), не растягивается на ячейку сетки или
ширину формы. Ряд кнопок — в `.form-buttons`.

- Обычное действие (назад, отмена, Добавить AI-решение, вторичное):
  `.btn.btn-secondary`. В строке таблицы — `.btn-small`.
- Главное действие формы (Сохранить, Отправить, Добавить, Создать,
  PDF, Войти): `.btn` — та же геометрия, заливка `--accent`, белый
  текст. Эталон заливки — кнопка «PDF» в конструкторе листка.
- Разрушительное текстовое действие («Удалить выбранные» и т.п.):
  `.btn.btn-danger`.
- Компактный вариант в строке таблицы или панели инструментов:
  `.btn-small` — только где полный размер ломает строку.

Не класть `.btn` последней ячейкой сетки: `justify-items: stretch`
раздует её на всю колонку. Кнопку выносить в `.form-buttons` под сеткой.

### Отступы в формах

Не подбирать зазор «чуть больше / чуть меньше» и не прыгать через
ступень. Шкала уже задаёт ритм:

| Токен | px | Где использовать |
| ----- | -- | ---------------- |
| `--space-1` | 4 | Внутри компактного контрола (иконка у текста, чипы в строке). **Не** между полем и кнопкой. |
| `--space-2` | 8 | Поле ↔ кнопка действия, связанные контролы в одном блоке. Эталон: `margin` у `.ws-add-text textarea` и `gap` у `.form-buttons`. |
| `--space-3` | 12 | Заголовок / `summary` ↔ содержимое, которое оно открывает; между секциями формы. |
| `--space-4`…`--space-6` | 16–32 | Между крупными блоками страницы, не внутри одной формы. |

Если кнопка «слишком далеко», сначала проверьте, не выше ли соседнее
поле остальных (разный `rows`) и не сложились ли два отступа. Не
сжимайте поле↔кнопку до `--space-1`.

Символ закрытия / точечного удаления (`×`) — небросный `.icon-btn`,
как «Удалить листок» в списке листков и «Убрать из листка» в конструкторе.
Не `.btn.btn-danger` и не красная плашка. Hover: цвет `--err` и лёгкий
розовый фон. Исключение: крестик закрытия боковой панели (`#sidebar-close`)
— элемент хрома, не этот стандарт.

### Уведомления пользователя

Основной формат — тост `#ws-saved` / `.ws-saved` в правом нижнем углу
(как «Сохранено ✓» при автосохранении). Зелёный фон — успех, красный
(`.ws-saved-error`) — ошибка. Показ: `EgorAutosave.showSaved(ok, message)`.

- Краткое подтверждение действия (`messages.success` / `messages.info`)
  рендерится как `.msg-success.ws-toast-src`: без JS это обычная плашка,
  `autosave.js` прячет её и показывает тост.
- Не пишите новые плашки `.msg-success` сверху страницы и не дублируйте
  тост баннером в контенте.
- `.msg-error` / `.msg-warning` оставляем только когда сообщение должно
  остаться на странице (ошибка формы, диагностика PDF, предупреждение
  на задании). Логин (`login.html`) и страница ошибки LaTeX — такие
  устойчивые случаи, не тосты.

Главная ловушка: если добавили новый utility-класс в шаблон и не пересобрали
CSS, локально всё хорошо (браузер отдаёт старый `app.css` из кэша или файл
уже содержит класс), а после мержа стиль пропадает. Поэтому `make check`
перед коммитом и та же проверка в CI.

Вторая ловушка — кэш браузеров на проде: `.htaccess` отдаёт статику с
`max-age` 7 дней. Раньше это лечили ручным `?v=N` у `app.css` и скриптов,
и один пропущенный bump (CSS холста, сентябрь 2026) оставил учеников на
неделю со старыми стилями. Теперь на проде `core.staticfiles.HashedStaticFilesStorage`:
`collectstatic` в `deploy.sh` кладёт файлы с хэшем содержимого в имени
(`app.6afbb756ab6c.css`), `{% static %}` подставляет эти имена, и после
деплоя браузеры берут новые файлы сразу. `?v=N` в шаблонах можно не трогать
(на проде он лишний, локально безвреден). Исходник `css/input.css` из
обработки исключён, файла вне манифеста хранилище не боится.

## 3. Проверки перед коммитом

```bash
make check
```

Цель делает три вещи: пересобирает `app.css`, гоняет тесты
(`manage.py test`, 84 штуки) и падает, если пересобранный `app.css` отличается
от закоммиченного.

Сообщение `app.css не под git — добавьте его в коммит` значит, что файл ещё не
отслеживается: `git diff` про untracked-файлы молчит, поэтому проверка была бы
фиктивной. Достаточно `git add public_html/static/css/app.css`.

Отдельно:

```bash
make build-css   # только пересборка
make test        # только тесты
```

## 5. Цикл «обновления → PR → ревью → правки → повторное ревью»

Прямые коммиты в `main` не используем — только ветки и pull request.

```
правки локально → проверка на localhost → make check → ветка + PR в GitHub →
  ревью и правки → доработка (снова сначала localhost) →
  push исправлений в ту же ветку → повторное ревью → merge в main
```

1. Агент работает в отдельной ветке (от актуального `main`) и открывает PR с
  описанием: что менялось, какие экраны затронуты, что проверено.
   **Первый шаг всегда локальный**: изменение реализуется и проверяется
   вручную на localhost до того, как попадёт в PR (см. раздел
   «Сначала localhost, потом Git» в AGENTS.md).
2. Ревью — inline-комментарии в PR: автоматические от
  `.github/workflows/claude-review.yml` (метки `[P1]…[P3]`) плюс ручные
   от человека.
3. Правки по ревью уходят **новыми коммитами в ту же ветку**. Не используем
  `--amend` и force-push: иначе комментарии ревьюера отвязываются от строк и
   историю правок становится не видно.
4. **Ответ в каждом треде обязателен.** После каждого пуша агент запускает
   `tools/pr.sh status`, разбирает все замечания (в том числе появившиеся
   после предыдущего круга) и отвечает через `tools/pr.sh reply` в каждом
   inline-треде, помеченном «⚠ без ответа»: подтверждённое — «исправлено
   в <sha>» с сутью правки, спорное — аргументированный отказ. Тред без
   ответа автора PR — незавершённая работа, PR к повторному ревью не готов.
5. Ветка с исправлениями пушится в GitHub повторно — начинается новый круг
  ревью тех же или новых замечаний. Повторяем 2–5, пока не будет апрув.
6. После апрува — merge в `main`.

### Как агент пушит ветку и открывает PR сам

У агентов (Claude, Codex) нет SSH-ключа, поэтому для GitHub используется
fine-grained personal access token владельца репозитория, выданный только на
`emukhin96/egormath` с правами **Contents: read/write** и **Pull requests:
read/write** (для статуса CI в `status` — ещё **Checks: read**). Токен лежит
в `.secrets/GITHUB_TOKEN` (каталог в `.gitignore`), в чат и в логи он не
попадает никогда. Срок действия ограничен — по истечении просто положить
новый файл.

Всё, что нужно агенту, собрано в `tools/pr.sh`, который умеет ровно три
вещи и ничего сверх пайплайна:

```
tools/pr.sh push                        # текущая ветка → GitHub, только fast-forward
tools/pr.sh open "Заголовок" body.md    # PR ветка → main (если уже открыт — покажет ссылку)
tools/pr.sh open "Заголовок" body.md feat/base   # стек: PR поверх ещё не слитой ветки
tools/pr.sh status                      # состояние PR, замечания ревью (с id, «⚠ без ответа»), CI
tools/pr.sh reply <id> "Текст"          # ответ в треде замечания: что и в каком коммите исправлено
```

Правила остаются прежними и не зависят от того, что токен технически
позволяет больше:

- merge, rebase, force-push и любые коммиты в `main` агент не делает
  никогда — сливает только человек, вручную, после апрува;
- правки по ревью — новые коммиты в ту же ветку, затем снова `tools/pr.sh push`
  и ответ в каждом треде через `tools/pr.sh reply` с номером коммита;
  `status` считает тред без ответа, пока последнее слово в нём не за автором
  PR, и перечисляет такие id — их список должен быть пустым;
- ветку удалять после merge тоже не нужно — это делает GitHub при слиянии
  или владелец.

Скрипт сам отказывается работать из `main` и не принимает `--force`;
защита ветки `main` в GitHub (ruleset «только через PR, без force-push»)
для приватного репозитория на бесплатном плане недоступна, поэтому
единственная гарантия здесь — дисциплина агента и ревью.

Чеклист PR:

- [ ] `make check` проходит
- [ ] `app.css` пересобран и лежит в коммите рядом с `input.css`
- [ ] Скриншоты затронутых экранов
- [ ] Вручную пройдены: логин, кабинет учителя, кабинет ученика, база задач,
  ```
  конструктор листка (drag-and-drop, звёзды, автосохранение), проверка работы
  ```
- [ ] Формулы KaTeX рендерятся
- [ ] `tools/pr.sh status` не показывает тредов «⚠ без ответа»: на каждое
  inline-замечание есть ответ автора PR (коммит с исправлением или почему нет)
- [ ] Результат виден на localhost ДО пуша: изменение сначала реализовано
  ```
  и проверено в рабочей копии, в ней оставлена ветка со всем сделанным
  (при стеке PR — верхняя ветка стека или интеграционная сборка),
  `runserver` показывает всё — см. раздел «Сначала localhost,
  потом Git» в AGENTS.md
  ```



## 6. CI

`.github/workflows/ci.yml` на каждый push и pull request:

1. Python 3.12 (как в CI и Docker-образе; код совместим с 3.10–3.13), `pip install -r requirements.txt`
2. `manage.py test`
3. Скачивание Tailwind CLI, пересборка CSS и `git diff --exit-code` по
  `app.css` — защита от забытого `make build-css`

CI не деплоит: на Timeweb входящий SSH из GitHub Actions режется.
После merge в `main` запустите на сервере `deploy/deploy.sh`.

## 7. Автоматизация pipeline (кандидаты на будущее)

Сейчас ревью и merge делает человек вручную. Следующие шаги для более
автоматического pipeline — по мере необходимости, без обязательства внедрять
всё сразу:

- **Branch protection на** `main` в настройках GitHub-репозитория: запретить
push напрямую, требовать зелёный CI (`test`) и минимум один апрув перед
merge. Закрепляет правила из раздела 5 на уровне GitHub, а не только
договорённостью.
- **Автоматический код-ревью PR** — уже работает:
`.github/workflows/claude-review.yml` оставляет inline-комментарии
с находками (`[P1]…[P3]`). Охват: обычные PR из веток этого репозитория;
draft-PR и PR из форков workflow пропускает (условие job `analyze`).
Авторизация — секрет `CLAUDE_CODE_OAUTH_TOKEN` (подписка Claude, токен
выпускается командой `claude setup-token`); промпт и схема ответа —
в `.github/claude/`.
Правки по ним — обычные новые коммиты в ветку PR.
- **Авто-merge после апрува**: `gh pr merge --auto --squash` или GitHub
"Auto-merge" на PR — сливает сам, как только выполнены required checks и
апрув, без ручного клика, но команду merge всё равно инициирует человек.
- **CI-задачи для агентов**: добавить в `ci.yml` шаги, которые запускают
`.cursor/agents/tex-checker.md`-подобные проверки (например, компиляцию
тестового `.tex`) на каждый PR, а не только вручную перед PR.
