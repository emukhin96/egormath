# Pipeline разработки

Как сейчас работает проект: разработка идёт локально, изменения уезжают в
GitHub (`git@github.com:emukhin96/egormath.git`) через ветки и pull request'ы.
Деплой на Timeweb отложен —
[deploy/DEPLOY.md](../deploy/DEPLOY.md) держим как справочник на будущее.

Короткая версия для AI-агентов (команды, конвенции, чеклист) — в
[AGENTS.md](../AGENTS.md) в корне репозитория.

## 1. Локальная работа

Первый запуск:

```bash
python3.10 -m venv venv
./venv/bin/pip install -r requirements.txt
cd public_html
../venv/bin/python manage.py migrate
../venv/bin/python manage.py seed_topics
../venv/bin/python manage.py createsuperuser
```

Ежедневно — два терминала:

```bash
# терминал 1: сайт
cd public_html && ../venv/bin/python manage.py runserver

# терминал 2: пересборка стилей при правках шаблонов и CSS
make watch-css
```



## 2. Стили


| Файл                               | Роль                                                              |
| ---------------------------------- | ----------------------------------------------------------------- |
| `public_html/static/css/input.css` | Единственный источник: токены, `@layer base`, `@layer components` |
| `public_html/static/css/app.css`   | Собранный артефакт, **коммитится вместе с исходником**            |
| `tools/tailwindcss`                | Standalone CLI, качается автоматически, в git не попадает         |


Правила:

- Токены отступов — шкала 4px: `--space-1` … `--space-6`. Новые значения
берём из шкалы, а не «на глаз».
- Tailwind preflight обнуляет отступы и вес заголовков. Всё, что должно
выглядеть как обычный текст (`p`, списки, `h1`–`h6`, `hr`), уже
восстановлено в `@layer base` — не переопределять поштучно в шаблонах.
- Повторяющийся набор утилит выносим в `@layer components`, а не копируем
длинную строку `class="..."` по шаблонам.
- Именованные классы (`.btn`, `.card`, `.ws-*`) — стабильный контракт для
шаблонов и JS, не переименовывать без необходимости.
- Запрещены акцентные рамки с одной стороны (`border-top/left/right/bottom`
цветом `--accent` и т.п.): выделять панели только фоном или тенью.
- Основные разделы приложения живут только в горизонтальной навигации
`base.html`. Боковая панель заполняется через `{% block sidebar %}` и содержит
только контекст открытой страницы: фильтры, метаданные, сводку и действия.
- Переиспользуемые панели лежат в `public_html/templates/includes/sidebar/`.
На экране до 760px панель открывает `static/js/shell.js`; при изменении
разметки сохраняйте ID `context-sidebar`, `context-toggle`,
`sidebar-close` и `sidebar-backdrop`.

### Уведомления пользователя

Основной формат — тост `#ws-saved` / `.ws-saved` в правом нижнем углу
(как «Сохранено ✓» при автосохранении). Зелёный фон — успех, красный
(`.ws-saved-error`) — ошибка. Показ: `EgorAutosave.showSaved(ok, message)`.

- Краткое подтверждение действия (`messages.success` / `messages.info`)
  уходит в этот тост через скрытый `.ws-toast-src` в `base.html`.
- Не пишите новые плашки `.msg-success` сверху страницы и не дублируйте
  тост баннером в контенте.
- `.msg-error` / `.msg-warning` оставляем только когда сообщение должно
  остаться на странице (ошибка формы, диагностика PDF, предупреждение
  на задании). Логин (`login.html`) и страница ошибки LaTeX — такие
  устойчивые случаи, не тосты.

Главная ловушка: если добавили новый utility-класс в шаблон и не пересобрали
CSS, локально всё хорошо (браузер отдаёт старый `app.css` из кэша или файл
уже содержит класс), а после мержа стиль пропадает. Поэтому `make check`
перед коммитом и та же проверка в CI.

## 3. Проверки перед коммитом

```bash
make check
```

Цель делает три вещи: пересобирает `app.css`, гоняет тесты
(`manage.py test`, 84 штуки) и падает, если пересобранный `app.css` отличается
от закоммиченного.

Сообщение `app.css не под git — добавьте его в коммит` значит, что файл ещё не
отслеживается: `git diff` про untracked-файлы молчит, поэтому проверка была бы
фиктивной. Достаточно `git add public_html/static/css/app.css`.

Отдельно:

```bash
make build-css   # только пересборка
make test        # только тесты
```



## 4. Ветки и коммиты

- Ветки: `feat/<что>`, `fix/<что>`, `ui/<что>`, `docs/<что>`.
- Сообщения коммитов — на русском, по сути изменения, в стиле истории
репозитория («Кабинет учителя: плитки счётчиков и приоритет проверки»).
- Не коммитим: `venv/`, `db.sqlite3`, `media/`, `.secrets/`,
`public_html/staticfiles/`, `tools/tailwindcss` — всё уже в `.gitignore`.



## 5. Цикл «обновления → PR → ревью → правки → повторное ревью»

Прямые коммиты в `main` не используем — только ветки и pull request.

```
правки локально → проверка на localhost → make check → ветка + PR в GitHub →
  ревью и правки → доработка (снова сначала localhost) →
  push исправлений в ту же ветку → повторное ревью → merge в main
```

1. Агент работает в отдельной ветке (от актуального `main`) и открывает PR с
  описанием: что менялось, какие экраны затронуты, что проверено.
   **Первый шаг всегда локальный**: изменение реализуется и проверяется
   вручную на localhost до того, как попадёт в PR (см. раздел
   «Сначала localhost, потом Git» в AGENTS.md).
2. Ревью — inline-комментарии в PR: автоматические от
  `.github/workflows/codex-review.yml` (метки `[P1]…[P3]`) плюс ручные
   от человека.
3. Правки по ревью уходят **новыми коммитами в ту же ветку**. Не используем
  `--amend` и force-push: иначе комментарии ревьюера отвязываются от строк и
   историю правок становится не видно.
4. Ветка с исправлениями пушится в GitHub повторно — начинается новый круг
  ревью тех же или новых замечаний. Повторяем 2–4, пока не будет апрув.
5. После апрува — merge в `main`.

Чеклист PR:

- [ ] `make check` проходит
- [ ] `app.css` пересобран и лежит в коммите рядом с `input.css`
- [ ] Скриншоты затронутых экранов
- [ ] Вручную пройдены: логин, кабинет учителя, кабинет ученика, база задач,
  ```
  конструктор листка (drag-and-drop, звёзды, автосохранение), проверка работы
  ```
- [ ] Формулы KaTeX рендерятся
- [ ] Результат виден на localhost ДО пуша: изменение сначала реализовано
  ```
  и проверено в рабочей копии, в ней оставлена ветка со всем сделанным
  (при стеке PR — верхняя ветка стека или интеграционная сборка),
  `runserver` показывает всё — см. раздел «Сначала localhost,
  потом Git» в AGENTS.md
  ```



## 6. CI

`.github/workflows/ci.yml` на каждый push и pull request:

1. Python 3.10, `pip install -r requirements.txt`
2. `manage.py test`
3. Скачивание Tailwind CLI, пересборка CSS и `git diff --exit-code` по
  `app.css` — защита от забытого `make build-css`

CI не деплоит: деплой появится отдельным шагом, когда вернёмся к Timeweb.

## 7. Автоматизация pipeline (кандидаты на будущее)

Сейчас ревью и merge делает человек вручную. Следующие шаги для более
автоматического pipeline — по мере необходимости, без обязательства внедрять
всё сразу:

- **Branch protection на** `main` в настройках GitHub-репозитория: запретить
push напрямую, требовать зелёный CI (`test`) и минимум один апрув перед
merge. Закрепляет правила из раздела 5 на уровне GitHub, а не только
договорённостью.
- **Автоматический код-ревью PR** — уже работает:
`.github/workflows/codex-review.yml` оставляет inline-комментарии
с находками (`[P1]…[P3]`). Охват: обычные PR из веток этого репозитория;
draft-PR и PR из форков workflow пропускает (условие job `analyze`).
Правки по ним — обычные новые коммиты в ветку PR.
- **Авто-merge после апрува**: `gh pr merge --auto --squash` или GitHub
"Auto-merge" на PR — сливает сам, как только выполнены required checks и
апрув, без ручного клика, но команду merge всё равно инициирует человек.
- **CI-задачи для агентов**: добавить в `ci.yml` шаги, которые запускают
`.cursor/agents/tex-checker.md`-подобные проверки (например, компиляцию
тестового `.tex`) на каждый PR, а не только вручную перед PR.
